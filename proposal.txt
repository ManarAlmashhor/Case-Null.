Abstract
This research proposal presents case: null, an educational digital-forensics investigation
platform in which discrete mathematics powers evidence-based reasoning. The proposed
application combines an interactive evidence board with a deterministic inference engine that
represents suspects, access permissions, login records, and device activity using sets,
predicates, Boolean matrices, and binary relations. When an investigator selects a clue, the
system updates the set of candidates who remain consistent with the evidence and displays
the corresponding mathematical explanation. A separate consistency checker distinguishes
mutually contradictory statements from incomplete or unknown information. The proposal is
grounded in published work on formal digital-forensic reasoning and evidence graphs, while
deliberately limiting its scope to fictional, controlled cases rather than real-world criminal
attribution. An implementation and evaluation plan is provided to test reasoning correctness,
explanation traceability, interaction usability, and educational value. No experimental results
are claimed, because the platform has not yet been implemented or tested.
Keywords: discrete mathematics; digital forensics; propositional logic; set theory; binary
relations; explainable reasoning; educational software
1. Introduction
Digital investigations increasingly involve heterogeneous records: account permissions,
authentication events, computer usage, and communications. Converting such records into
defensible conclusions requires explicit reasoning and evidence traceability. Formal
approaches have been investigated for network-forensic reconstruction (Liu et al., 2015),
while the NIST SP 800-86 guidance describes forensic collection, examination, analysis, and
reporting from an information-technology perspective (Kent et al., 2006).
case: null adapts these principles into a classroom-scale interactive environment. Instead of
asking an AI model to guess a culprit, the proposed software encodes the evidence as
transparent conditions and uses mathematical operations to determine which fictional
suspects remain compatible with those conditions. The dramatic detective-style interface
motivates interaction; the reasoning engine must remain reproducible, inspectable, and
mathematically correct.
1.1 Problem statement
A visually compelling investigation simulation can obscure the reasoning process when it
presents suspect decisions without showing the logic behind them. Conversely, a conventional
truth-table or set calculator can demonstrate mathematics without showing why it matters in
practical computing. The project addresses this pedagogical gap by presenting formal
reasoning and interactive case investigation in a single system.

1.2 Research question and objectives
Research question: Can an interactive, rule-based investigation system accurately filter
candidates against simulated digital evidence and explain each decision in terms of discrete
mathematical operations?
• Model fictional investigative facts using sets, predicates, functions, relations, and Boolean
matrices.
• Implement deterministic candidate filtering and contradiction checks without inventing
missing evidence.
• Visualize evidence connections and display an explanation for every candidate inclusion or
exclusion.
• Evaluate algorithmic correctness and user comprehension using predefined cases and
objective rubrics.
2. Literature Review
2.1 Digital-forensics process and evidence analysis
NIST SP 800-86 provides practical guidance for integrating digital-forensic techniques into
incident response, including examination of files, operating systems, networks, and
applications (Kent et al., 2006). It also cautions that technical guidance is not a substitute for
applicable legal procedures. case: null therefore imitates investigation steps for educational
purposes; it does not claim evidentiary admissibility or real-world investigative authority.
2.2 Logic-based forensic reconstruction
Liu et al. (2015) proposed a logic-based model that links digital evidence to system
vulnerabilities and reconstructs plausible attack scenarios. Case: Null applies the same general
idea of explicit reasoning to a fictional investigation by using set operations to determine
which suspects remain consistent with the verified clues.
2.3 Knowledge representation and explainability
Casey et al. (2017) developed a specification for representing digital evidence, recording its
origins, and linking related items across investigative tools. More recently, Lee et al. (2025)
proposed DF-graph, which structures communications evidence in a knowledge graph and
emphasizes traceable explanations. These studies motivate the project’s separation of
evidence records, inference rules, and explanation output. They do not establish that the
proposed case: null interface is novel or that its future educational outcomes will be positive.

3.1 Formal candidate filtering
Let U be the finite set of fictional suspects, E₁, E₂, …, Eₖthe sets of suspects satisfying each
selected verified clue, and Cₖthe remaining candidates after processing k clues. The filtering rule
is:
C₀ = U and Cₖ = Cₖ₋₁ ∩ Eₖ

Equivalently, Cₖ = U ∩ E₁ ∩ E₂ ∩ … ∩ Eₖ. Thisintersection is a mathematicalstatement about
compatibility with selected conditions; it does not infer guilt. If a clue is unverified or itstruth
value is unknown, it should not be treated as a mandatory exclusion condition.
3.2 Binary relations and matrices
Let F represent the set of files. A permission relation R is a subset of U × F, in which (u, f) ∈ R
means user u can access file f. A 0–1 incidence matrix M can encode whether each user
satisfies a given evidence condition. For a candidate whose required entries are all 1, the
conjunction evaluates to true. This is a Boolean operation, not ordinary arithmetic matrix
multiplication.
3.3 Inductive correctness argument
Base case: before any clue is processed, the algorithm returns C₀ = U, so every candidate
satisfying the empty collection of clues remains. Induction hypothesis: after k clues, Cₖ
contains exactly those members of U satisfying all k clues. Inductive step: processing clue k+1
returns Cₖ₊₁ = Cₖ ∩ Eₖ₊₁. The resulting set contains exactly the candidatessatisfying the previous k
clues and clue k+1. Therefore the invariant holds for any finite number of processed clues.
3.4 Counting possible clue selections
For n independently selectable binary clue controls, there are 2ⁿ possible subsets of selected
clues. With six controls, there are 2⁶ = 64 selection patterns. The number of valid candidates
under any selection must still be computed from the selected evidence; counting alone cannot
identify a culprit. More complex extensions may count ordered event sequences or
combinations of multiple actors.
4. Proposed System Design
The prototype is planned as a browser-based application with four logically separate modules:
a synthetic evidence repository, an inference engine, an interactive evidence board, and an
explanation/report module. This separation helps ensure that visual interactions cannot
silently change the underlying inference rules.

4.1 Core functional requirements
• Load fictional cases containing suspects, permission records, computer events,
timestamps, and evidence-source metadata.
• Let the investigator select or deselect clues, causing immediate recomputation of
candidate sets.
• Show evidence connections on a draggable, node-based investigation board.
• Display the exact set operation, applicable rule, and reason behind each exclusion.
• Report an empty candidate set as a consistency warning rather than assuming a new
culprit.
• Export a case summary containing the selected evidence and the trace of reasoning.
4.2 Implementation approach
The simplest version can use Python, sets, dictionaries, SymPy for propositional-logic
satisfiability checks, and Streamlit for the interface. A more visually polished implementation
can use React and React Flow for draggable evidence cards connected by edges, with a Python
service providing deterministic filtering. These choices are supported by official library
documentation (SymPy Development Team, n.d.; Streamlit, n.d.; React Flow, n.d.).
4.3 Handling missing and conflicting evidence
A critical design rule is to distinguish true, false, and unknown facts. A missing login record
does not necessarily prove that a person was not logged in. Clues have metadata: source,
time, reliability status, and whether they are mandatory or provisional. Verified mandatory
clues affect the set intersection; disputed facts remain visible but do not automatically
eliminate a candidate. Conflicting statements should generate an inconsistency alert, not a
forced suspect selection.
4.4 User interface and case narrative
The interface follows a cyber-noir investigation theme, with a central evidence corkboard,
panels for suspects and case files, and a mathematical-analysis section. Clicking a suspect
reveals their profile and relation to each record; selecting a clue updates the candidate list and
a stepwise trace. The interface is a proposed visualization, not a screenshot of finished
software.
5. Proposed Research Methodology
5.1 Research design
A design-and-evaluation methodology is proposed. The system would first be implemented
against manually specified fictional cases, then tested for logical correctness and interaction
quality. The initial research question concerns whether the rule engine behaves correctly and
can explain its output; it does not investigate crime-prediction accuracy.

5.2 Case construction and baseline
Create a small synthetic case collection (e.g., five to ten scenarios) with five to eight suspects
each, six to ten clues per case, and ground-truth sets of candidates for each selected-clue
configuration. Include cases with no clues, one remaining candidate, multiple candidates,
incompatible mandatory clues, and explicitly unknown facts. A manually verified truth-table or
set-based solution provides the baseline against which application output is compared.

5.4 Ethical and academic safeguards
All names, portraits, accounts, and logs in the planned demonstration should be fictional or
explicitly consented to. No real individual should be accused or ranked as suspicious. The
program’s output should be labeled “logically possible candidates” rather than “guilty
suspect.” Further, access to a user account is not proof that its owner personally performed
an action. These boundaries are essential for responsible educational use.

A minimal viable product needs only one well-defined fictional case, five suspects,
approximately six clues, a working mathematical trace, and contradiction handling. Additional
case dialogue, animated strings, and character narratives are secondary features. This scope
keeps the discrete mathematics visible and the implementation realistic for an undergraduate
project.
7. Discussion and Limitations
The strongest educational contribution is the transformation of abstract concepts into
inspectable computer operations: set intersection corresponds to candidate filtering;
predicates correspond to evidence constraints; relations correspond to permissions; and
induction explains why the algorithm remains correct after each clue. This connection is
consistent with the broader role of discrete mathematics in reasoning about algorithms and
systems (Lehman et al., 2015).
However, a deterministic rule engine is only as sound as the input assumptions. The same
records may admit several plausible explanations; an event associated with an account is not
conclusive personal identification; timestamps can be incorrect; and missing logs can create
false impressions. Moreover, the current proposal uses a simplified Boolean model and does
not address probabilistic uncertainty, chain of custody, or courtroom admissibility. Results
from the proposed evaluation are not yet available, and project novelty cannot be established
without a dedicated prior-art review.
8. Conclusion
Case: Null is a feasible, research-grounded Discrete Mathematics project that applies logic,
sets, and relations to a simulated digital investigation. Prior research demonstrates the
relevance of logic, structured evidence, and explainable analysis in digital forensics. The
proposed classroom prototype shows how mathematical rules connect evidence to each
result. The next step is to implement the prototype and evaluate it against clear benchmarks.

A.2 Chapter 1 — Logic and Proofs: predicates, connectives, quantifiers
Define predicates P(x), T(x), and W(x) from the three evidence columns. The first-stage
eligibility rule is:
Eligible(x) = P(x) ∧ T(x) ∧ W(x)
For Sara, Eligible(S) = 1 ∧ 1 ∧ 1 = 1. For Omar, Eligible(O) = 0 ∧ 1 ∧ 0 = 0. The proposition

Ax ∈ U Eligible(x), is false. The implication Eligible(x) ⇒ P(x) follows from the definition of
Eligible(x).
Next define N(x) to mean that no validated physical-location evidence excludes x from being

PhysicalCandidate(x) = P(x) ∧ T(x) ∧ W(x) ∧ N(x)

A.4 Chapter 3 — Mathematical Induction: algorithm correctness
The candidate-filtering algorithm maintains an invariant. If E1, E2, …, Ek are selected
mandatory clue sets, then after processing k clues the program retains precisely the
candidates satisfying every one of those clues:
C₀ = U; Cₖ = Cₖ₋₁ ∩ Eₖ
Base case (k = 0): No conditions have been applied, so C₀ = U. Every identity is correctly
retained.
Inductive hypothesis: Assume Cₖ = U ∩ E1 ∩ … ∩ Ek, i.e., the set of identitiessatisfying the first k
clues.
Inductive step: Processing clue Ek+1 gives Cₖ₊₁ = Cₖ ∩ Ek+1 = U ∩ E1 ∩ … ∩ Ek ∩ Ek+1. Thus the
invariant also holds for k + 1. By mathematical induction, the algorithm is correct for any finite
number of selected verified clues.

Each clue may be selected or not selected, giving 2 choices per clue. By the fundamental
counting principle, the six controls produce 2⁶ = 64 possible clue-selection patterns. If the
investigator must choose exactly three of the six clues, the number of combinations is C(6, 3) =

from five suspects would be C(5, 2) = 10.
These counts quantify possibilities; they do not determine guilt or give probabilistic
confidence. The actual candidatesfor any chosen clue combination still require the logical set
intersection.

A.7 Integrated live demonstration and proposed output
Step 1: Open the case; five suspects appear as movable cards, and the research file,
workstation, logs, and alibi appear as evidence cards. Step 2: The professor activates E1, E2,
and E3. The logic panel shows Eligible(x) = P(x) ∧ T(x) ∧ W(x), the mathematical panel displays
P ∩ T ∩ W = {S, K}, and the relations matrix identifies which accounts correspond to which
resources.
Step 3: The professor reveals the verified alibi E4. The screen shows C₄ = {K}, updates the
matrix and the activity log, and displays the inductive explanation of why the filtering
procedure retains only candidates meeting every chosen clue. Step 4: The counting panel
shows “64 clue-selection patterns,” “20 ways to choose three clues,” and “10 hypothetical
suspect pairs.” Step 5: The professor can deselect E4, returning {S, K}, or select a deliberately
incompatible verified clue to trigger a contradiction warning. A case report records the
selected clues, their sources, the set operations, the relation links, and the final list of logically
possible candidates.
Interpretation and limitation. Underthisfictional case’sstated physical-presence assumptions,
Khalid is the only remaining candidate after the fourth clue. This is not proof that Khalid
leaked the file, and it is not a prediction about any real individual. An actual forensic
investigation would require independent validation, alternative hypotheses, and careful
attention to missing or compromised records.
